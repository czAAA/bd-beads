# 55: Убрать сохранение с пути правки каждой ячейки

**Что сделать:** рисование больше не переписывает всю Библиотеку схем на каждой ячейке, а неудачное сохранение становится видимым вместо молчаливого.

Сейчас каждая закрашенная во время протяжки ячейка перечитывает и переписывает все сохранённые Схемы: полный разбор библиотеки, проход нормализации по каждой Схеме в ней, затем синхронная запись всего целиком — по разу на каждое движение мыши. На библиотеке из 10 обычных Схем 60×90 это примерно 3 мс работы с JSON плюс синхронная запись около 1 МБ, на каждую ячейку. А если запись превысит квоту хранилища браузера, она выбросит исключение там, где его никто не ловит: правка теряется, и пользователь не видит ни малейшего признака этого.

- **Библиотека схем переезжает в composable**, который владеет Схемами, тем, какая из них открыта, и сохранением.
- **Все изменения Схемы уже проходят через одно место.** Это место начинает планировать сохранение, а не выполнять его, поэтому протянутый штрих пишется один раз по завершении, а не по разу на ячейку. Все остальные правки — создание, удаление, загрузка из файла, Очистить всё, Заменить бисер, Отменить, Повторить — сохраняются ровно как сейчас.
- **Неудачное сохранение становится видимым**: состояние «не удалось сохранить» в интерфейсе, на обоих языках, вместо непойманного исключения.

Намеренно **вне** объёма: предупреждение «хранилище почти заполнено». Тикет 56 поднимает потолок примерно с 50 Схем до примерно 1600, и предупреждать о такой стене — значит предупреждать о препятствии, до которого годы. Если тикет 56 будет отменён или застрянет, предупреждение нужно добавить сюда — это и есть условие срабатывания.

**Блокируется:** 54 (отказ от флага расширенного Отражения) — после удаления ветвлений по флагу App.vue заметно меньше, и вынос composable становится куда меньшим диффом

**Статус:** ready-for-agent

**Решения (2026-09-17):**
- Сохранение становится подписчиком библиотеки, а не шагом на пути правки. Схемы в памяти и так источник истины; сохранение должно следовать за ними, а не стоять у них на пути.
- Сохранение идёт через единую точку, а не через `watch`. `watch` по библиотеке срабатывал бы на любое реактивное изменение, включая обновление отметки времени у каждой ячейки штриха, и тогда корректность начала бы зависеть от дебаунса. Проход через уже существующую единую точку фиксации даёт то же свойство «невозможно забыть» без этой хрупкости.
- Выносится только один composable. Остальные части App.vue — редактор и история, настройки Отражения, Выделение с буфером — выносятся тогда, когда этого потребует конкретный тикет, а не ради самого рефакторинга. Разовая перестройка файла на 1150 строк за 663 тестами — ровно тот случай, который трудно ревьюить и легко сломать.
- Отдельные ключи хранилища на каждую Схему намеренно исключены. Они снижают объём перезаписи, но не общий размер, а сохранение по завершении штриха и так убирает стоимость на каждую ячейку. Вернуться к этому только если рисование всё ещё будет подтормаживать.
- У Excalidraw, ближайшего аналога среди локальных приложений такого рода, открыта задача ровно этой формы (excalidraw/excalidraw#8395): за пределами квоты сохранение молча отказывает, и пользователи теряют доски целиком. Сделать отказ видимым — минимально необходимое исправление.

- [ ] Протянутый штрих Кистью или стиранием пишет в хранилище один раз, по завершении штриха, а не по разу на ячейку
- [ ] Создание, удаление и загрузка Схем, а также Очистить всё, Заменить бисер, Отменить и Повторить по-прежнему сохраняются
- [ ] Библиотека схем и её сохранение живут в одном composable, который можно тестировать без монтирования приложения
- [ ] Упавшая запись в хранилище оставляет видимое состояние «не удалось сохранить», на английском и на русском
- [ ] После перезагрузки приложение показывает те же Схемы без изменений
- [ ] Весь набор тестов зелёный
