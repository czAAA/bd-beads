# The visual check

Part of the testing docs; the rules every test follows are in [`docs/testing.md`](../testing.md), and when to update the reference screenshots is its Visual baselines.

`npm run visual` drives the production build in a real browser (Playwright, Chromium) through every spec in `e2e/visual/`. It runs in CI's own container (`scripts/visual.sh`, the Playwright image `ci.yml` names) whenever Docker is running, so what it draws is what CI draws; without Docker it runs on this machine only on Linux, where the first run needs the browser (`npx playwright install chromium`). Arguments go to Playwright: `npm run visual -- e2e/visual/look.spec.ts`. To look at a failure, open `playwright-report/index.html` (`npx playwright show-report`). CI runs it on every pull request ([`ci.md`](ci.md)).

A spec is one of three kinds, told by what it compares with:

1. **The Project grid against its references** (a spec that compares through `e2e/support/referenceCheck.ts`, such as `look.spec.ts`): fixture Projects drawn in the app, and the drawn grid compared with the reference screenshots in `e2e/visual/__screenshots__`. Each scenario (`e2e/visual/scenarios.ts`) is shot upright at 100% and 300% zoom, and rotated at 100% (`zoomsFor`: rotation and zoom are independent in the renderer). Only the grid is compared, not the rulers or other text, since fonts differ between machines and the beads do not.
2. **A part of the screen against the runner's own screenshot** (a spec that calls `toHaveScreenshot`; `grep -l toHaveScreenshot e2e/visual/*.spec.ts` lists them): a panel, a sheet, a dialog, a page of the Homepage, the Canvas in a look the grid references don't hold. Playwright compares pixel by pixel, within the tolerance the spec gives. What differs from one build or machine to the next (the Version, the browser's name) is given a fixed text before the shot, not masked: a mask is as wide as the value under it.
3. **What the app does in a real browser, with no picture**: every other spec. It opens the app as a person would and asserts on the page: the offline shell ([`browser-checks.md`](browser-checks.md)), addresses, where a panel lands, what a reload keeps.

The grid references were made from the one-element-per-bead grid the renderer replaced (ticket 103), and are what the renderer is held to ("visually indistinguishable", ADR 0018). A canvas never lands on exactly the same pixels as the DOM did, so the comparison is two checks (`e2e/support/referenceCheck.ts`): a look check (both images reduced to the average color of blocks a fraction of a bead wide, at most a per-Technique share of blocks may differ) and a content check (every bead's centre is its color, finished rows' greys included). The check tests itself: `look.spec.ts` renders Projects with a bead recolored or missing, and a Row progress marker the reference does not have, and expects the comparison to fail.

The references are made and checked on Linux, in the image CI runs. A reference drawn by macOS's Chromium differs by a few pixels of text and edge: CI fails on it, and fails again on the run after the fix, so on a Mac `npm run visual` stops when Docker isn't running rather than draw on macOS (`BD_VISUAL_NATIVE=1` draws there anyway, to look, never to commit). On an arm64 Mac the image runs as arm64; `BD_VISUAL_PLATFORM=linux/amd64` draws on CI's own architecture, emulated and slower, if a reference still differs. The container's Linux `node_modules` are installed once per lockfile into `~/.cache/bd-beads/visual`, shared by every worktree; the checkout's own are never touched. Without Docker, on Linux, it uses this machine's Playwright: the same version as CI, not the same image. Which command rewrites which kind, and when that is right, is in [`docs/testing.md`](../testing.md) (Visual baselines): `npm run visual:update` rewrites the second kind's screenshots that differ, `UPDATE_REFERENCES=1` the first kind's, and neither is run to make a failing check pass.
