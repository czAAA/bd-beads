# Patterns are stored in a compact grid encoding, not moved to IndexedDB

[ADR 0001](0001-local-only-persistence.md) decided *that* the Pattern library lives in this browser's localStorage. This decides *how* those bytes are shaped, and it is a decision about a ceiling: localStorage gives roughly 5MB, and until now a Pattern spent it on one JSON object per cell, each carrying a full `#rrggbb` string. A 60×90 Pattern — 9×13.5cm in 1.5mm cubes, an ordinary size — measured **102.9KB**, so the library filled up at roughly 50 Patterns. Storing each Pattern's distinct colours once, and its cells as run-length-encoded indexes into that table, takes the same Pattern to **2.9KB**: room for roughly 1,600. A 150×200 Pattern goes from **570.9KB to 14.9KB**. Encoding and decoding a ten-Pattern library also turned out **~4.4× faster** than today's plain JSON round trip (3.5ms → 0.8ms), because the bytes JSON has to walk are what dominates either way.

**The encoding, not IndexedDB.** IndexedDB would remove the quota ceiling outright, which is strictly more than this does. It also does nothing whatsoever about size — the same per-cell objects would simply be large somewhere else — and it is asynchronous, so it would put a promise in front of every read and write, on an edit path ticket 55 ([ADR 0012](0012-saving-follows-the-pattern-library.md)) has just finished making synchronous and funnelled. Two orders of magnitude of headroom for a synchronous `encode → setItem` is the better trade for a personal tool. **Migrate to IndexedDB if a Pattern library ever approaches the quota despite this encoding, or if save latency becomes visible** — those are the two things this decision is betting against, and either one happening means the bet has lost.

**Run-length encoding over a raw index array.** A raw array of one index per cell is perfectly predictable — 1 byte per cell, no design beats it and none loses to it — but that predictability only matters near a ceiling this removes, and in localStorage a byte array pays a 33% base64 tax that only IndexedDB would avoid. RLE is far smaller on the blocky, banded designs beadwork actually produces, and it does not lose to *today's* format even on a worst case where every neighbouring cell differs: that grid measures 10.8KB against today's 105.8KB, because even a run of length one costs a couple of characters rather than a whole object with a hex string in it.

**Each Pattern carries its own colour table, not indexes into the Palette.** A cell may hold any hex at all: a Custom color, or a colour from an imported Pattern this device's Palette has never had ([ADR 0002](0002-palette-separate-from-bead-catalog.md) keeps the Palette a painting convenience rather than the set of legal colours, and Bead quantities already counts hexes the Palette doesn't know). A Palette-indexed encoding would have had nothing to write for those cells and would have destroyed them silently on the next save.

**This colour table is not, and must not become, Image colors.** Convert image stores the colours one conversion found and freezes them ([ADR 0011](0011-image-colors-stored-frozen.md)); this table describes the hexes the grid holds right now. They differ the moment a colour is erased, and both are then correct. Merging them looks like an obvious deduplication and would silently destroy that feature, so the encoding keeps the table inside the grid's own stored value and passes every other Pattern field through untouched — including fields added after this ADR, which is what keeps the two structurally separate rather than merely separate by intent.

**Exported Pattern files keep today's readable JSON, at file version 1.** A Pattern file exists to move work between devices and to be read by a human who wants to know what is in it; there, legibility is worth more than compactness, and ADR 0001 makes it the only way work moves at all. Export and import are therefore an encode/decode boundary rather than a passthrough: the compact form exists only between `savePatterns` and `loadPatterns`.

**The stored format carries a version.** Today's format has none — it is a bare JSON array of Patterns — so the reader sniffs that one shape, calls it version 1, and reads a version out of the envelope for everything since; a Pattern saved in version 1 decodes to exactly the values it had and is rewritten compact by the next save. A third format needs only another entry in the reader table, not another ad hoc sniff.

**Considered options**: gzip (or `CompressionStream`) over today's JSON (rejected — it would compress well, but it is asynchronous, it makes the stored value opaque to inspection, and it leaves the per-cell object shape in place so a future format change has to happen anyway); storing only non-empty cells as a sparse map of position to hex (rejected — smaller than today on a lightly painted grid, but it is worst on exactly the finished, fully painted Patterns that actually fill the quota); one storage key per Pattern (rejected in ADR 0012 for write amplification reasons and equally beside the point here — it does not change total size); a proactive "storage nearly full" warning instead of shrinking anything (rejected — ADR 0012 deferred that warning to this encoding precisely because it moves the wall from a plausible 50 Patterns to an implausible 1,600; **if this encoding is ever dropped, that warning comes back**).
