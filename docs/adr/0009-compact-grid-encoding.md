# Projects are stored compactly in localStorage; Project files stay readable JSON; both carry a version

**Status: accepted.** Tickets 56, 233.

[ADR 0001](0001-local-only-persistence.md) puts the Project library in this browser's localStorage, about 5MB. This decides how its bytes are shaped, and how a Project file is shaped.

**Stored compactly.** Each Project stores its distinct colors once, and for every row that has a bead, where its beads start and the beads as runs of indexes into that table (`domain/projectEncoding.ts`). Only rows with a bead are written, so an empty canvas costs nothing and a far-off bead costs one row. A 60×90 Project is about 3KB instead of about 100KB as an object per bead: room for roughly 1,600 ordinary Projects instead of 50. The encode and decode are faster than plain JSON, because the bytes dominate either way. The 60×90 figures are what the storage tests assert.

- **The color table is per Project, not indexes into the Palette**: a bead may hold any hex ([ADR 0002](0002-palette-separate-from-bead-catalog.md)), and a Palette-indexed encoding would have nothing to write for one the Palette lacks.
- **The table is not, and must not become, Image colors** ([ADR 0011](0011-image-colors-stored-frozen.md)): one describes the beads now, the other what a conversion found. They differ the moment a color is erased and both are then correct. The table stays inside the beads' stored value, and every other Project field passes through untouched.
- **The stored value carries a version.** The reader table reads every version it knows (1, a bare array of Projects with a fixed grid; 2, the envelope with beads by position and a Frame) and the next save rewrites it in the current one.
- **A version this build can't read is kept, not stepped over.** A save writes the whole library from memory ([ADR 0012](0012-saving-follows-the-pattern-library.md)), so `loadProjects` copies an unreadable value to a second key before carrying on empty: a stale cached build meeting a newer build's library must not wipe it. No recovery UI and no refusal to start.

**Project files stay readable JSON.** A file exists to move work between devices and to be read by a person, so legibility wins over size; export and import are an encode/decode boundary, and the compact form exists only between `saveProjects` and `loadProjects`. A file carries its kind (`bd-beads/pattern`, `bd-beads/library`) and a format version; the reader refuses a kind or version it doesn't know rather than guessing, reads 1 and 2, and writes only 2. With no backend to migrate stored data, every migration happens on read.

**Considered options**: IndexedDB (rejected for now: removes the quota but not the size, and puts a promise in front of every read and write on a synchronous edit path; **move to IndexedDB if a library nears the quota despite this encoding, or save latency becomes visible**); gzip or `CompressionStream` over JSON (rejected: asynchronous and opaque); a sparse map of position to hex (rejected: worst on finished, fully painted Projects); one key per Project (rejected in ADR 0012); a "storage nearly full" warning instead (rejected: the encoding moves the wall years away; **if this encoding is ever dropped, that warning comes back**).
