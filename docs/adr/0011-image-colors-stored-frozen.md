# Image colors are stored frozen, not derived from the grid

Convert image ([ADR 0010](0010-convert-image-fixed-physical-size.md), ticket 58) extracts a small set of colors from a picture. That set is saved on the Pattern as Image colors and never changes afterwards — even though the same set could be recomputed at any moment by walking the grid, which `computeColorQuantities` already does for Bead quantities. Storing it is what makes a converted Pattern editable at all: the Colors group otherwise offers only the twelve fixed Palette swatches plus one Custom color slot, and a Pattern converted from a picture matches none of them, so correcting a single bead would mean re-entering a hex by hand.

Frozen rather than kept in sync with the grid. Any rule that adds newly painted colors or drops erased ones is derivation wearing a hat, and it brings edge cases with it: what to do when Replace Bead's resampling happens to drop a color, whether a color erased and then repainted keeps its place in the list, what order a growing list is shown in. Freezing gives the field one unambiguous meaning — the colors this conversion found — at the cost of a list that can drift from what the grid currently holds. That cost is acceptable because the Palette and Custom color remain available alongside it, so a drifted list never blocks an edit.

**This deliberately coexists with a second, derived color list, and the two must not be merged.** Ticket 56's compact storage encoding gives every Pattern a colour table of the distinct hexes actually present in its grid. The moment a color is erased from a converted Pattern, that table and Image colors differ, and both are correct: the encoding's table describes the grid as it stands, Image colors describes the conversion that produced it. Folding one into the other looks like an obvious deduplication and would silently destroy the feature.

**Considered options**: deriving the set from the grid on demand instead of storing it (rejected — it is free and self-maintaining, and would also fix the unrelated annoyance that a Pattern painted with several Custom colors can only reach the last of them, but it changes the Colors group for every Pattern in the library rather than only for converted ones). Quantizing the picture to the twelve Palette colors was originally rejected too, for costing fidelity and silently collapsing two similar extracted colors into one; near-exact snapping was kept instead, catching only an extracted color within an imperceptible distance of a Palette color. **Amended (ticket 177): that rejection is superseded.** Convert image now quantizes every resolved color to its nearest current-Palette color unconditionally, not only a near-exact one — every median-cut box's representative color is matched to the nearest of PALETTE's twelve hexes (see `resolveImageColors`/`nearestColor` in `src/domain/imageColors.ts`), so two similar extracted colors can now collapse onto the same Palette entry. Near-exact snapping's distance threshold and its merge-avoidance guard (refusing to snap two colors near the same Palette entry) are gone, subsumed by unconditional nearest-match quantization. The fidelity loss ADR 0002 warned about is now an accepted tradeoff: a converted Pattern's Image colors are now always a subset of the same twelve Palette colors every other Pattern paints with, rather than a closed set of picture-only hexes nothing else in the app can reach — one color story instead of two, at the cost of flat artwork with near-identical shades losing the distinction. The lowered max-colors floor (`MIN_IMAGE_COLORS`, now 1) follows from this: reducing all the way to a single Palette-matched silhouette color is no less meaningful than reducing to two, now that every result is already restricted to the twelve. The thing that would genuinely make a Pattern's colors purchasable is a catalog of real bead colors; `Bead.color` is null for all three catalog entries today, and filling it is a separate feature.
