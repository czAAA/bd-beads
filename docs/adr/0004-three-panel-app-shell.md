# App shell is a four-panel tool layout, scoped to bd-beads' own features

_Amended by [ADR 0005](0005-tools-above-canvas.md): editing tools (tool picker, palette, undo, mirror, row progress) moved from the main panel to the above-canvas panel. The rest of this ADR — the four regions themselves, and the main panel's role for the New Pattern form — still holds._

_Amended by ticket 35: "New Pattern" is no longer an above-canvas control — it moved into the top bar's aqua summary box, as the first item before the current-Pattern summary and the language switcher. The zoom controls moved off the above-canvas panel too, into a floating stack on the canvas box's own right edge (see [ADR 0005](0005-tools-above-canvas.md)'s amendment). The above-canvas panel's only remaining content is the Toolbox._

_Amended by ticket 39: the below-canvas panel opens with a dimmed horizontal divider as wide as the canvas column, followed by exactly three boxes in this order: Beads needed, Saved Patterns, Export and import. The Bead catalog box is removed ([ADR 0007](0007-one-bead-per-pattern-no-color-mapping.md))._

_Amended by ticket 51: "New Pattern" moves again, from the top bar's aqua summary box into the below-canvas Saved Patterns box (ticket 39), as the first control in that box. Zoom controls move again too, from the floating right-edge stack to a compact cluster fixed to the canvas box's top-right corner. _Amended by ticket 57: ticket 51's "canvas box" wording for zoom's anchor was implemented against the Pattern's own sized box (`PatternCanvas.vue`), one level too deep — corrected to the surrounding **canvas** panel itself (`App.vue`'s `.app-shell__canvas`), so the cluster stays fixed to that panel's top-right corner regardless of the Pattern box's own size, position, zoom or scroll offset within it._

_Amended by ticket 55: the top bar gains a second row of its own, below the title and summary boxes, used for a notice about the Pattern library as a whole rather than the open Pattern — today only the "couldn't save" notice ([ADR 0012](0012-saving-follows-the-pattern-library.md)). It is part of the top bar, not a fifth panel, and it only takes up space while there is something to say. Library-wide notices go here; everything else still follows "How to apply" below._

The app shell is organized as a top bar plus four panels (see ticket 14): a **main panel** on the left (the New Pattern form today; painting/fill/mirror tools from tickets 07-09 join it later), and on the right, stacked around the canvas itself, a panel **above the canvas** (always-visible actions like "New Pattern"), the **canvas** in its own box, sized to the open Pattern within a screen-bounded maximum (see ticket 16 for its zoom behavior and ticket 18 for the box's shape; the zoom controls live in the above-canvas panel), and a panel **below the canvas** (the saved-Patterns switcher, per ticket 05's original "list of saved Patterns... below the pattern canvas"). New UI is placed into one of these regions by function rather than each ticket inventing its own screen or nav pattern.

This layout only hosts features bd-beads actually has or has planned. Conventions common in general-purpose drawing/design tools (login/accounts, a gallery, animation, an image library/objects panel, a generic layers panel, object clone/flip/shadow controls) are deliberately not adopted, since bd-beads is a single-user, local-only tool for a fixed domain (beadwork patterns), not a general drawing app — see [ADR 0001](0001-local-only-persistence.md).

A panel with no feature assigned to it yet (e.g. the main panel while a Pattern is open, before tickets 07-09 land) renders an explicit greyed-out "coming soon" placeholder (`t.shell.mainPanelPlaceholder`) rather than blank space, so the shell's shape stays visible ahead of its content.

**How to apply:** when writing a new ticket that adds UI, place it in the main panel (a tool/canvas-setup control), above the canvas (an always-visible action), or below the canvas (a Pattern-level/cross-cutting view) per this convention, and don't add chrome modeled on generic drawing-app features that aren't part of bd-beads' scope. If a panel would otherwise sit empty, give it the placeholder treatment instead of leaving it blank.

**Considered options**: letting each new feature ticket place its own controls ad hoc (rejected — already caused rework once layout needed reorganizing, see ticket 14); adopting the full feature set of reference drawing apps for future-proofing (rejected — adds unused surface area to a personal single-user tool with a narrow, fixed domain); leaving not-yet-built panels blank (rejected in favor of the placeholder — a panel with literally nothing in it reads as broken rather than as scaffolding).
