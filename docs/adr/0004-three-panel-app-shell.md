# App shell is a four-panel tool layout, scoped to bd-beads' own features

The app shell is organized as a top bar plus four panels (see ticket 14): a **main panel** on the left (the New Pattern form today; painting/fill/mirror tools from tickets 07-09 join it later), and on the right, stacked around the canvas itself, a panel **above the canvas** (always-visible actions like "New Pattern"), the **canvas** in its own fixed-size box (see ticket 16 for its zoom behavior), and a panel **below the canvas** (the saved-Patterns switcher, per ticket 05's original "list of saved Patterns... below the pattern canvas"). New UI is placed into one of these regions by function rather than each ticket inventing its own screen or nav pattern.

This layout only hosts features bd-beads actually has or has planned. Conventions common in general-purpose drawing/design tools (login/accounts, a gallery, animation, an image library/objects panel, a generic layers panel, object clone/flip/shadow controls) are deliberately not adopted, since bd-beads is a single-user, local-only tool for a fixed domain (beadwork patterns), not a general drawing app — see [ADR 0001](0001-local-only-persistence.md).

A panel with no feature assigned to it yet (e.g. the main panel while a Pattern is open, before tickets 07-09 land) renders an explicit greyed-out "coming soon" placeholder (`t.shell.mainPanelPlaceholder`) rather than blank space, so the shell's shape stays visible ahead of its content.

**How to apply:** when writing a new ticket that adds UI, place it in the main panel (a tool/canvas-setup control), above the canvas (an always-visible action), or below the canvas (a Pattern-level/cross-cutting view) per this convention, and don't add chrome modeled on generic drawing-app features that aren't part of bd-beads' scope. If a panel would otherwise sit empty, give it the placeholder treatment instead of leaving it blank.

**Considered options**: letting each new feature ticket place its own controls ad hoc (rejected — already caused rework once layout needed reorganizing, see ticket 14); adopting the full feature set of reference drawing apps for future-proofing (rejected — adds unused surface area to a personal single-user tool with a narrow, fixed domain); leaving not-yet-built panels blank (rejected in favor of the placeholder — a panel with literally nothing in it reads as broken rather than as scaffolding).
