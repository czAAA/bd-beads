# Saving follows the Pattern library instead of sitting on the edit path

[ADR 0001](0001-local-only-persistence.md) decided *that* the Pattern library lives in this browser's localStorage. This decides *when* it is written, and what happens when the write is refused.

The Pattern library, which Pattern is open, and persistence live together in one composable, `usePatternLibrary` (ticket 55). Every Pattern change — create, remove, import, paint, Fill, Paste, Mirror, Rotate, Row progress, Delete all, Replace Bead, Undo, Redo — goes through one of its mutators, and nothing outside it touches storage. A save writes the whole library from memory: the in-memory Patterns are the source of truth, so a save follows them rather than reading storage back to merge into it, which is what a save used to do (a full parse of the library plus a normalise pass over every Pattern in it, before writing one changed Pattern).

**Saving is funnelled, not watched.** A `watch` over the library would give the same can't-forget property, but it would fire on every reactive change, including each individual cell of a dragged stroke — which would make the deferral below load-bearing for correctness rather than only for speed. Routing through the single commit point instead keeps the deferral a performance detail: forget to flush and the change is still in memory, still on screen, still undoable, and the next save (any other edit, or leaving the page) carries it, because a save always writes the whole library.

**One edit defers its save: a dragged paint or erase stroke.** Painting used to write once per mousemove; on a ten-Pattern library of ordinary 60×90 Patterns that was roughly 3ms of JSON work plus a synchronous write of about 1MB, per cell. The per-cell path now marks the save pending and the stroke's end performs it, so a stroke of any length writes once. A stroke released outside the document fires no mouseup on the page, so `pagehide` and the editor's own teardown flush too; that leaves no window in which an edit is both unsaved and unrecoverable.

**A refused write is visible.** localStorage throws when a write doesn't fit, and that throw used to escape uncaught from the middle of the paint path, losing the edit with no sign at all — Excalidraw, the closest local-first peer to this app, has an open data-loss issue of exactly that shape ([excalidraw#8395](https://github.com/excalidraw/excalidraw/issues/8395)). The library now catches it, keeps the change pending for the next save to retry, and raises a `saveFailed` state that the top bar shows as a "couldn't save" notice in both languages until a save gets through. The notice belongs to the top bar rather than to one of [ADR 0004](0004-three-panel-app-shell.md)'s four panels: it is about the whole library, not the open Pattern, and has to be visible whether or not a Pattern is open.

A proactive "storage nearly full" warning is deliberately not part of this. Ticket 56's compact grid encoding moves the ceiling from roughly 50 Patterns to roughly 1,600, which turns a proactive warning into a warning about a wall years away; **if that encoding is dropped or stalls, add the warning.**

**Considered options**: debouncing every save behind a timer (rejected — a debounce that can silently drop the last write is exactly the fragility the funnel avoids, and it would still have to be flushed on leaving the page); one storage key per Pattern (rejected — it reduces write amplification but not total size, and saving on stroke end already removes the per-cell cost; **revisit if painting still feels sticky**); extracting App.vue's other slices — editor/history, Mirror settings, Selection and clipboard — at the same time (rejected — each comes out when a ticket needs it, since a big-bang restructure of a 1150-line file behind hundreds of tests is hard to review and easy to regress).
