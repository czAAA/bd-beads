# A Pattern's grid is its size; millimetres are an estimate, and Replace Bead keeps the grid

Supersedes [ADR 0008](0008-replace-bead-recalculates-grid.md). Amends [ADR 0010](0010-convert-image-fixed-physical-size.md) for Patterns sized in beads.

A Pattern used to store its real-world size (`widthMm`/`heightMm`) as the source of truth and derive `columns × rows` from it and the Bead's footprint. That made "keep the real-world size fixed" the natural answer to Replace Bead (ADR 0008). It also hid a truth about how the piece is actually made: a weaver counts beads, and the millimetres are how big that count happens to come out, which varies with thread tension, slack and bead-to-bead tolerance. The stored millimetres were never more than a request that got rounded to a whole number of beads.

So the grid is now the size. The New Pattern form takes its size in **beads** by default (alongside mm and cm), and an mm or cm size is converted to a grid once, at creation, and then forgotten. The Pattern no longer stores `widthMm`/`heightMm`. What the editor shows in millimetres is an **estimated size**, computed on demand from the grid and the Bead: width is `columns × (widthMm + widthCorrectionMm)` and height is `rows × heightMm`, the exact inverse of the conversion that turns a stated size into a grid, so typing 30mm never estimates back to something other than about 30mm. The estimate is always shown as an estimate (with a warning tooltip) because it ignores what a real piece does: thread slack, tension, and the tighter row packing peyote actually has, which the canvas already draws (`rowHeightPx`) but the mm-to-grid conversion never used. Reconciling those is deliberately left for later rather than folded into this change.

Consequences:

- **Replace Bead keeps the grid** for every Pattern, whichever unit it was created in. Columns, rows and painted cells are untouched; only the Bead (and so the estimated size) changes. It is no longer a resample, so it no longer resets Row progress or Mirror axis counts, whose grid is unchanged. The confirmation says the estimate changes and that the user can adjust rows and columns afterwards to bring it back to the size they want.
- **Changing rows and columns on an open Pattern** becomes a first-class edit (a Size Tool group): it exists because the old "recalculate the grid to hold the size" answer is gone, and someone who swaps to a bigger bead needs a direct way to trim back. It is disabled while Row progress is on, since a shrinking grid would invalidate finished rows; shrinking drops the cells it removes, and it is one undo step.
- **A total-cell cap** (10,000 cells, columns × rows) applies when creating a Pattern and when growing one, in every unit. It is set from a measured cost of about 3.4µs per cell per painted cell (the whole grid is rebuilt and re-diffed on each), which puts a 100 × 100 grid at roughly 34ms per step. It never blocks opening, editing or shrinking a Pattern that is already over it, such as an imported one.
- **Convert image** still fits a picture into a fixed frame (ADR 0010), but the frame is now the grid's own physical footprint, so for a Pattern sized in beads there is no separate millimetre size to honour: the frame is whatever those beads measure.

**Considered options**: keeping the real-world size authoritative only for Patterns created in mm or cm (rejected — two behaviours for the same command depending on a fact the Pattern would have to remember and the user would not see, and the stored millimetres were a rounded request in either case); keeping both a stored size and a grid and letting them drift (rejected — a second source of truth that is wrong the moment anything edits the grid); making the estimate technique-aware now (rejected for this change — it would make the estimate disagree with the size the user typed until the mm-to-grid conversion is reconciled with peyote's row packing too).
